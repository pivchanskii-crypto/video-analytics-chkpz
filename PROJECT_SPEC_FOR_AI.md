### 3.2. Координаты зон и пути к кадрам

По ТЗ, не по модели:

- `zones.polygon` — JSON точек. Каждая координата относительная, диапазон 0…1, чтобы полигон не съезжал при другом разрешении.
- Число вершин ТЗ не ограничивает. Предметная область ограничивает полигон 3–8 точками в долях кадра.
- Попадание человека в зону: по умолчанию нижняя середина рамки (ноги на полу). Способ можно сменить в `config.yaml`. В предметной области это единственный способ, без оговорки про замену.
- `violations.frame_path` — путь к кадру с разметкой в файловом хранилище (S3-совместимое или том на диске). В базе лежит путь, не сам файл.
- Кадр ложной тревоги ТЗ кладёт в отдельный каталог хранилища. Имя каталога не задано. Дообучение в работу не входит.
- `faces.photo_path` — путь к эталонному фото. Рядом в базе эмбеддинг.
- В JSON-лог решения модели пишутся рамки, классы и уверенность. Эмбеддинг в этот лог не пишется.

Предметная область хранит у события один кадр-подтверждение (кадр, на котором удержание уже выполнилось) и не хранит круглосуточный архив. Непрерывный архив завода остаётся у действующей системы видеонаблюдения.

### 5.2. Что говорят документы (два разных правила)

ТЗ, раздел 7. Одинаковое событие — та же камера, та же зона, тот же тип и тот же человек (`track_id`, а для известного лица ещё и сотрудник). Пока человек не ушёл из зоны или из кадра, повторная запись и повторное письмо не создаются. Новый вход после ухода создаёт новую запись. Порог пребывания по умолчанию 3 секунды, настраивается; проход короче порога событием не становится. Два основания у одного человека — две записи: отдельно `no_ppe` и отдельно `unauthorized`. Итог «допущен» хранится в журнале и не попадает в ленту и в письмо.

Предметная область, другое правило. Удержание по умолчанию 3 секунды. Пока событие этого типа ещё «Новое», второе такое же не пишется. После квитирования повтор возможен не раньше заданного интервала, по умолчанию 60 секунд, и только если ситуация снова есть. Ключ «тип + ещё не квитировано», без `track_id`. Личность не устанавливается.

Имена `thresholds.zone_stay_seconds` и `presence_ttl_seconds` **не наблюдались**. ТЗ хранит порог пребывания в `config.yaml` и не задаёт отдельный TTL трека. Предметная область задаёт интервал повтора 60 секунд после квитирования, это не TTL присутствия в Redis.

Очередь с именем `violations_queue` **не наблюдалась**. ТЗ: воркер шлёт событие в backend только через брокер; брокер не выбран. Имя ключа, тип структуры (list, stream, pub/sub), схема сообщения и потребитель неизвестны.

Правила, которые ТЗ уже формулирует как таблицу решений (их можно брать как требования, не как реализованный код):

| Условие | Результат |
| --- | --- |
| Камера `disabled` | Анализ не выполняется |
| `ppe_always`, нет обязательного СИЗ | `no_ppe` на всём кадре |
| Зона `ppe_in_zone`, человек внутри дольше порога, СИЗ неполные | `no_ppe` с зоной |
| Зона `ppe_in_zone`, человек в СИЗ | Нарушения нет |
| Нет СИЗ вне таких зон, `ppe_always` выключен | Нарушения нет |
| Зона `zone_only`, внутри дольше порога | `zone_entry`, СИЗ не проверяются |
| Пребывание короче порога | События нет |
| Распознавание включено, список допуска зоны пуст | Допуск не проверяется, лицо только подписывается |
| Список задан, сотрудник в списке | «Допущен»: в журнал, не в ленту и не в письмо |
| Список задан, известный сотрудник не в списке | `unauthorized` |
| Список задан, лица нет в базе | `unauthorized`, подпись «неизвестный» |
| Сходство ниже порога или лицо не найдено, допуск включён | Имя не ставится, `uncertain`, запись в ленте и письмо |
| Тот же человек, та же зона, тот же тип, ещё в кадре | Новая запись и новое письмо не создаются |

Обязательное СИЗ — все классы, отмеченные обязательными в конфигурации. «Без СИЗ» — отсутствует хотя бы один. Стартовый набор: `person`, `helmet`, `safety_vest`. `work_clothing`, `safety_glasses`, `respirator` — только после подтверждения предприятия.

Смена флагов камеры, зон и допусков должна доходить до воркера не дольше чем за 5 секунд и без перезапуска. Как это сделано (poll конфига, pub/sub, версия строки) — **не наблюдалось**.

Анализ по ТЗ: 1 кадр в секунду (каждый 30-й при 30 fps). Поток камеры: RTSP, 1920×1080, H.264, Hikvision. Целевой контур 500+ камер; приёмка — 4 потока.

Предметная область CV-модули описывает иначе: сменный модуль на кадр возвращает класс, рамку и уверенность; ядро не содержит весов. Первый набор модулей — каска и жилет, запретная зона, дым и открытый огонь. Дыма и огня в ТЗ нет. Распознавания лиц в предметной области нет: «Личность человека в кадре система не устанавливает».

### 6.2. Что задано ТЗ

- Письмо уходит назначенным операторам камеры только по новой записи нарушения.
- В письме есть кадр с разметкой. Как прикрепляется (MIME `image/*`, ссылка, CID) — **не наблюдалось**.
- От кадра с нарушением до отправки — не больше 60 секунд. На проверочном видео это должно выполняться для каждого нарушения.
- Если срок сорван, факт пишется в лог и администратор получает отдельный алерт.
- Каждая попытка отправки хранится: канал, получатель, время, статус (`alerts`). Допустимые значения `status` не названы. Перехода `pending` → `failed` в документах нет.
- Итог «допущен» письмо не порождает.
- Пока то же событие по тому же человеку не завершилось уходом из зоны или кадра, второе письмо не создаётся.
- Интеграция: почтовый сервер SMTP. Хост, порт, TLS, учётные данные — только из окружения, имена переменных не заданы.
- Имени `ALERT_DELIVERY_TIMEOUT_SECONDS` нет. Число 60 секунд в ТЗ — требование к сроку, не имя настройки.

Предметная область письма не предусматривает. Событие — запись для оператора, не команда станку, сирене или АСУ ТП. Сообщение ответственному цеха в AS-IS делает человек.

## 7. Real-time (WebSockets)

**Не наблюдалось** реализации `WS /api/v1/ws/violations`.

ТЗ говорит только это: лента оператора дополнительно приходит по `WebSocket /api/v1/ws/violations`; используется тот же JWT и тот же фильтр камер, что у HTTP. Оператор видит только назначенные камеры, администратор — все.

Не задано и в коде не видно:

- где лежит токен: query, заголовок `Sec-WebSocket-Protocol`, первое сообщение
- проверка подписи и отказ при просроченном access
- формат кадра (то же JSON, что `GET /violations`, или урезанное событие)
- рассылка: список соединений в процессе, Redis pub/sub, брокер
- что происходит при смене назначений камер у уже открытого сокета
- heartbeat и код закрытия

Предметная область WebSocket не упоминает. «Лента обновляется без перезагрузки» есть только в ТЗ (раздел 6.8), способ обновления кроме этого сокета не назван.

### 8.2. Как отдаётся видео

Реализации стриминга **не наблюдалось**. Эндпоинтов HLS, MJPEG, WebRTC и прокси RTSP в репозитории нет.

По документам:

- ТЗ: система принимает RTSP и показывает последний кадр (ссылка в карточке камеры). Если потока нет — состояние ошибки и повторное подключение не реже чем раз в 10 секунд. Простой дольше 60 секунд — алерт администратору. Запись потока не ведётся. Камера с `disabled` остаётся в списке и не анализируется. Нарушение хранит один размеченный кадр, не ролик.
- Предметная область: источник — файл-ролик на стенде или RTSP, если камера подключена. Прототип хранит событие и один кадр-подтверждение. Непрерывный архив пишет действующая система завода, прототип её не подменяет.
- AS-IS (`generate_asis.py`): «Показать поток на пост и писать архив» — это текущий ручной процесс поста, не функция разрабатываемого API.

Иных каналов живого видео (отдача потока клиенту) документы не описывают.
